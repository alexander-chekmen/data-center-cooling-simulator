How the system is wired

Two services, seven Modbus listeners, thirty simulated devices, and one deliberate rule: the collector must never know the equipment is simulated.

The whole system

Everything runs as two containers. The simulator owns the physics and serves it as Modbus registers. The api service polls those registers and serves the dashboard. Your browser talks to both — and that split is the point.

control · out of band telemetry · the monitored path

Why the two paths are separate

The collector reaches the simulator only over Modbus TCP. It contains no import, no config key and no branch that knows the other end is simulated. Point it at real hardware and the only thing that changes is the device inventory.

That is why control cannot travel the same path. If clicking a slider wrote into the telemetry stream, the pipeline would be proving nothing. Instead the browser holds two connections, and a control action is only visible once the collector has independently discovered its consequences by polling registers — typically 1–3 seconds later.

The physical analogy. This is the shape of a hardware test bench: the load bank is driven from one place, and the building management system that observes it is wired somewhere else entirely. Neither knows about the other.

What happens to one measurement

A single rack inlet temperature crosses six representations between the physics and the pixel. Each hop is a real place integrations break.

Where faults enter

Faults are injected at two different layers, and the distinction matters: one breaks the equipment, the other breaks your ability to see it.

The PDU gateway is the realistic bit: field devices routinely sit behind a single serial-to-TCP gateway and are distinguished by unit id, not by address. Reading offset 9 at unit 2 gives CDU supply temperature; the same offset at unit 3 gives rack power. The unit id decides what the address means.

What a poll cycle actually costs

Each device exposes 16–35 points across six poll classes with different cadences. A naive collector issues one request per point — roughly a thousand per second across the fleet, which collapses. Points are instead grouped into contiguous read windows across whichever classes are due together.

How a control action lands

  1. Browser → :8090Slider posts {"cpu":1.0,"gpu":1.0} to the control API. Nothing is written to the dashboard.
  2. Simulator state changesThe override enters current_load(), which the run loop feeds to step() on the next tick.
  3. Physics runsUtilization → power → heat → coolant and air loops → temperatures. Thermal mass makes this take minutes, not milliseconds.
  4. Registers re-encodeEvery point is projected from live state and encoded through the register map after each step.
  5. Collector discovers itThe next poll reads the changed registers over Modbus TCP and decodes them, rejecting anything outside its declared range.
  6. Dashboard updatesThe hub aggregates, the WebSocket pushes, the rack tile changes color — 1–3 seconds after the click, and minutes before the temperature finishes moving.
